# L8A — The UV Parameterization Problem
**Theme A1: UV Mapping + Texture Fundamentals | Stage 1 of 5**

---

## The Problem Without This Concept

You have a 3D mesh — a cube, a sphere, a character head. You want to paint detail on it: brick mortar lines, a face, wood grain. The detail is stored as a 2D image (a grid of pixels). You need a rule that answers: for any point on the 3D surface, which pixel in the 2D image should I read to get the color at that point?

Without a systematic answer to that question, you have no textures. Every polygon is flat-shaded at best.

The rule you need is called a **parameterization**. This lesson derives exactly what that means, why it is hard, and what the graphics pipeline does about it.

---

## Part A — Theory

### What a 3D Surface Actually Is

A triangle mesh is an approximation of a smooth surface. Mathematically, a smooth surface is a **2D manifold embedded in 3D space** — meaning it locally looks flat (like a 2D plane) everywhere you zoom in far enough, even though it curves in 3D.

That word "locally flat" is the key insight. A sphere is not flat globally, but zoom into any tiny patch of a sphere and it looks like a flat disc. The same is true for any smooth surface: skin, terrain, a car hood.

This local flatness means that any patch of a 3D surface can, in principle, be unrolled onto a flat plane. If the patch is small enough and does not have too much curvature, the unrolling barely distorts it.

Parameterization is the process of defining coordinates on the surface that let us refer to each point with two numbers — the same way latitude and longitude let us describe any point on Earth's surface with two numbers.

### The Mapping Problem: f: R³ → [0,1]²

We want a function:

```
f(x, y, z) = (u, v)
```

Given a 3D point on the surface, it returns 2D coordinates `(u, v)` in the range `[0,1]²`. Those coordinates are then used to look up a color in a texture image.

Why can't we just use x, y, z directly?

Consider the front face of a cube. Its points have x ∈ [-1, 1], y ∈ [-1, 1], z = 1. If we use (x, y) as our UV, we get a sensible mapping for the front face. But the right face has points with x = 1, y ∈ [-1, 1], z ∈ [-1, 1]. If we use (x, y) as UV on the right face too, the U coordinate (x) is always 1.0 — the entire right face collapses to a single vertical line in the texture. The texture on the right face would be a single-pixel-wide stripe stretched across the whole face. That is wrong.

World-space coordinates do not make good texture coordinates for anything other than surfaces that happen to face exactly one world-space axis.

### Forward Mapping vs Backward Mapping

There are two ways to think about the problem:

**Forward mapping** asks: given a texel (pixel in the texture) at position `(s, t)`, where does it land on the 3D surface? This is like a projector shining an image onto geometry. You push each texel forward and paint it onto whatever surface it hits.

**Backward mapping** asks: given a point on the 3D surface (or equivalently, a screen pixel), what texel should I read from the texture? This is what the GPU actually does. For each fragment generated by rasterization, the pipeline has a UV coordinate for that fragment (derived from the vertex UVs by interpolation), and it reads the texture at that coordinate.

Forward mapping is conceptually intuitive but computationally expensive and produces holes and overlaps when mapping from a flat texture onto a curved surface. Backward mapping is clean: every fragment reads exactly one texture lookup. No holes.

The entire texture mapping pipeline is based on backward mapping. Every UV coordinate you assign to a vertex is the answer to: "when rasterizing a fragment that falls on this vertex, which texture coordinate should the GPU use?"

### Why Perfect Parameterization Is Impossible

There is a fundamental mathematical result — the **Gaussian curvature theorem** — that says you cannot map a curved surface to a flat plane without distortion. Gaussian curvature measures how much a surface curves in all directions at a point.

You already know this intuitively: if you try to peel an orange and lay the peel flat without tearing, you cannot do it without the peel either stretching or folding. A sphere has positive Gaussian curvature everywhere. A flat plane has zero curvature. You cannot convert one to the other without distortion.

This is not a GPU limitation. It is not a software limitation. It is geometry.

For triangle meshes, this means:

1. Any parameterization of a curved surface will have **some distortion** — either the texture appears stretched in some regions or compressed in others, or the angles are not preserved.
2. The mesh must be **cut** along seam edges and unfolded into flat patches before it can be laid on a 2D plane. These cuts create discontinuities in the UV space (covered in L8D).

The goal of UV unwrapping is to minimize distortion while keeping the number of cuts (seams) small.

### The Easy Case: Parametric Surfaces

Some surfaces are already defined by a parameterization. A cylinder, for example:

```
x = r · cos(2π · u)
y = r · sin(2π · u)
z = v · h
```

Here `u ∈ [0, 1)` goes around the cylinder and `v ∈ [0, 1]` goes from bottom to top. The parameters `(u, v)` directly give positions on the surface. They are naturally normalized to [0,1].

For such a surface, we set `s = u` and `t = v` — the UV coordinates ARE the parametric coordinates. No work needed.

The same holds for spheres and tori. These surfaces have natural parameterizations built into their mathematical definition.

Most 3D mesh surfaces in games and film are NOT parametric in this sense. They are arbitrary triangle meshes. This brings us to the hard case.

### The Hard Case: Polygon Meshes

A triangle mesh has no natural parameterization. An artist-modeled head or a hand-sculpted terrain patch has no formula describing it. The only way to define a UV coordinate at each vertex is for an artist (or an algorithm) to manually "unwrap" the mesh.

UV unwrapping is the process of cutting the mesh along seam edges and then flattening each resulting patch so it lies in the 2D UV plane without overlapping. The artist in a 3D DCC tool (Blender, Maya, 3ds Max) opens the UV editor, marks seams on the mesh, runs an unwrap operation, and manually adjusts the resulting UV layout.

Automatic unwrapping algorithms exist (Least Squares Conformal Maps, ABF++, LSCM) but they always require human cleanup for complex meshes.

The key point: UV coordinates are **artist-assigned data** stored per-vertex in the mesh, not computed from geometry at runtime (in the standard pipeline).

### Industry Context

**Blender UV Editor**: after marking seams, `U → Unwrap` in edit mode runs the LSCM algorithm. The result is displayed in the UV editor as 2D "islands" floating in the [0,1]² space.

**Unreal Engine 5**: every `StaticMesh` has at least two UV channels. `UV Channel 0` is the material UV — the coordinates the material shader reads for color, roughness, and normal map. `UV Channel 1` is the Lightmass lightmap UV — a separate, non-overlapping parameterization used when baking indirect lighting. The Lightmass system calls `GenerateLightmapUVs` automatically if Channel 1 is not provided. These are two completely different parameterizations of the same mesh stored as two separate `vec2` attributes per vertex.

**Texture sets in Substance Painter**: a high-poly mesh is baked down to a low-poly mesh with UV-mapped textures. The UV layout of the low-poly mesh determines how detail from the high-poly mesh is stored in the baked texture. Bad UV layout = baking artifacts.

## Part B — Numeric Worked Example

### The Unit Cube UV Problem

Take a unit cube: 8 vertices at (±1, ±1, ±1). Six faces.

**Attempt 1: use world-space x and y as UV.**

Front face: z = 1. Vertices at:
- (-1, -1, 1) → UV = (-1, -1)
- ( 1, -1, 1) → UV = ( 1, -1)
- ( 1,  1, 1) → UV = ( 1,  1)
- (-1,  1, 1) → UV = (-1,  1)

Range of UV: x from -1 to 1, y from -1 to 1. Rescale to [0,1]: `u = (x+1)/2`, `v = (y+1)/2`. This works for the front face. The texture maps correctly across the face.

Right face: x = 1. Vertices at:
- (1, -1,  1) → UV using (x,y)/rescale = (1.0, 0.0)
- (1,  1,  1) → UV = (1.0, 1.0)
- (1,  1, -1) → UV = (1.0, 1.0)
- (1, -1, -1) → UV = (1.0, 0.0)

Look at the u values: they are all 1.0. Every vertex on the right face maps to U = 1.0. The entire right face collapses to a single vertical line at the right edge of the texture. Every fragment on the right face samples from the same column of texels. The texture is stretched across the face as a 1-texel-wide stripe.

This is the proof that world-space coordinates fail for anything other than the axis-aligned face that happens to face the right direction.

**Attempt 2: assign per-face UV.**

For the front face (z = +1), use (x, y) mapped to [0,1].
For the right face (x = +1), use (z, y) mapped to [0,1] — the two axes that actually vary on this face.
For the top face (y = +1), use (x, z) mapped to [0,1].

Each face gets its own local parameterization using the two non-constant axes. Each face maps correctly. The texture is not distorted on any face.

**Vertex count consequence**: the front face uses vertex at (-1,-1,1) with UV (0,0). The right face uses vertex at (1,-1,1) with UV (1,0) (since for the right face z=1 → u=1). These are the SAME 3D position but need different UVs. This means we need separate vertex entries for each face — covered in detail in L8D (seams).

## Pitfalls

**Pitfall 1: Using world-space position directly as UV**

Mistake: assigning UV = (worldPos.x / scale, worldPos.y / scale) in the vertex shader instead of using a UV vertex attribute.

Symptom: the texture "swims" — appears to slide across the surface as the object moves. This happens because the UV is computed from world position, which changes as the object transforms. The texture is no longer fixed to the surface.

Fix: always use a dedicated UV vertex attribute (layout location = 2 in the VBO). The UV is object-local data, not computed from world coordinates.

**Pitfall 2: UV coordinates outside [0,1] without understanding wrap modes**

Mistake: assigning UV = (2.5, 0.8) to a vertex without setting the wrap mode.

Symptom: the behavior is controlled by `GL_TEXTURE_WRAP_S` and `GL_TEXTURE_WRAP_T`. Default is `GL_REPEAT`, which tiles the texture (fract(2.5) = 0.5 → samples halfway through the texture). If you intended to use the full texture once, you get unexpected tiling.

Fix: understand that UV values outside [0,1] are valid — they trigger the wrap mode. Set the wrap mode explicitly: `glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_EDGE)` if you don't want tiling, or `GL_REPEAT` if you do.

**Pitfall 3: Confusing object-space UV with texture-space UV**

Mistake: thinking UV coordinates are in the same space as the 3D model coordinates.

Symptom: conceptual confusion when trying to scale or offset textures — adjusting vertex positions changes the geometry but does nothing to the UV.

Fix: recognize that UV is a completely separate coordinate system that happens to be stored per-vertex alongside position. Moving a vertex in 3D does not move its UV unless you explicitly change the UV attribute.
